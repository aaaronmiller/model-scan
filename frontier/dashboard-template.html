Current frontier: score versus task cost

Score is the weighted mean of AA’s ten v4.2 benchmark components, recomputed by ARDF; cost is AA’s workload cost per task in USD. These are benchmark workload costs, not your subscription bill. A frontier configuration is not dominated: no other configuration is at least as cheap and at least as good with one strict improvement. Zero is a price only when it is verified: an AA price of $0 stays in the comparison, on the $0 shelf at the left of the chart, only when a free route with the same name is listed in the pinned OpenRouter, Kilo or OpenCode Zen catalogs. An unverified free $0 (no such route, or a catalog lists a paid route) is held out of dominance, so it can neither dominate a paid model nor remove one from the frontier; it is listed after the table with its evidence. Unknown is not zero: configurations with a score but no published cost are listed as unpriced and are left out of the chart and of dominance. Configurations without every weighted benchmark are counted as unscored. No Priors value enters this panel, and nothing here needs the network.

Benchmark tier weighting (offline, from AA components)

The tier list is a subjective relevance preference, not a scientific quality score. Each tier multiplier scales its benchmarks’ AA v4.2 weight, then weights are renormalised. The default is 1 for every tier, which reproduces AA’s composite. A multiplier of 0 removes a tier, which can let configurations that lack those benchmarks be scored. Blank or out-of-range values (valid range 0 to 5) are rejected and the previous weights stay in force. This recalculation runs entirely in this page from the embedded per-benchmark scores.

Tiers: S = Terminal-Bench Science; A = Terminal-Bench 4.0; B = AA-Omniscience accuracy and non-hallucination; C = FrontierCode 2.0, HLE, GDP.pdf, CritPt; Unrated = AA-Briefcase, AutomationBench-AA. No D or F benchmarks appear in this mix.

    How to read the frontier

    The frontier is the set of configurations that no other configuration dominates: nothing else is at least as cheap and at least as good with one strict improvement. In the primary panel it is computed from Artificial Analysis v4.2 scores and AA task costs, and recomputed for whatever filters and tier weights you pick. In the multi-source ledger below it is the current-point frontier that blends sources through calibration. Frontier membership means “not dominated”, not “best for your task”: check effort, workload mix, quota, availability and privacy. Prices are benchmark workload costs, not bills, and a zero cost is a price while a missing cost is unknown.

    Archived essay from the August 2026 build (historical: its model names, prices, counts and script names are superseded)

    This essay was written for the August 2026 build (the v4.0 index scale, a 14-point frontier, GLM-5.2 and Muse Spark 1.2 corrections). It is kept unchanged as a record of that analysis. It is not a current ranking. Use the primary panel, the live frontier table and pareto-frontier-cheatsheet.md for current numbers. Commands it names (scripts/*.py) no longer exist; the build is python3 calibrate.py.

    This dashboard exists to answer a precise, operational question: for a given capability you need, what is the cheapest configuration that is not strictly dominated? Everything else — tiers, executor ratios, external cross-checks — is a different lens on the same calibrated plane. The graph is deliberately front-and-center because the calibrated capability–price plane is the only view that preserves provenance while remaining directly actionable. Overlays, tables, and filters are collapsed into dropdowns so the wall-map canvas stays maximal and readable, with a fullscreen toggle for detailed inspection.

    1. The plane and what it measures

    Every dot is one model × effort × harness × source × date observation projected onto two reference axes. Y is calibrated capability — the multi-source Arts-equivalent completion index anchored to Artificial Analysis Intelligence Index via exact model overlaps, not a raw benchmark score and not IQ. X is U.S. dollars per standardized task, calibrated to the same AA task-cost reference in log10 space. The task is not a single token: the estimator uses 12,000 input × price + 2,500 output × price adjusted by effort multipliers (high 1.1×/3.2×, xhigh 1.15×/4.75×, max 1.2×/8.5×) then fitted through overlapping models. Where the project has a direct measured task cost (Kilo, Vals, AA task cost), that evidence outranks the token-price estimate via the best_evidence_then_weighted_geometric_mean hierarchy. If a configuration has no defensible price, it does not receive an invented X — it lives on the unpriced shelf.

    Calibration is outside the browser. For each metric_axis × source_id × metric_name group, calibrate.py collapses repeats with a weighted median, finds exact model_key overlaps with the reference (AA), and fits four independent mappings: robust-affine Theil-Sen (median slope + median intercept, production default), Huber IRLS (δ 1.35), monotone piecewise isotonic, and auto-best per-group lowest RMSE. Each mapping writes cal_* columns with anchor count and RMSE as uncertainty. The dashboard only filters and aggregates those precomputed fields — it never recomputes coefficients. That is why the Pareto overlay is stable when you toggle log/linear or color modes.

    2. Why this looks different from v5 — and why that matters

    v5 collapsed to model-level means after requiring both axes, an implicit inner join that erased most capability-bearing configurations because task-cost evidence is inherently sparser than benchmark evidence. It then drew the frontier as the hero, making hundreds of configurations look like ten points. v7 preserves three honest states — paired, unpriced, unscored — and shows the full capability cloud behind the 14-point frontier. Aggregation happens after exploration, not before, so disagreement between sources (AA vs BenchLM vs Vals vs LiveBench) remains inspectable. Labels now scale to the cloud, not the sparse frontier.

    Old writing implied a single best model. This build separates three questions: (1) tiers classify calibrated capability alone — 4 real tiers: T1 Frontier ceiling ≥60, T2 Frontier ≥56, T3 Executor 47-56, T4 Utility <47 where the bottom 4 (glm/deepseek/luna/muse) are interchangeable and differentiated by context/reasoning/tool/cache within the same tier; (2) Pareto classifies economic non-dominance (cheaper + at least as capable); (3) executor ratio ranks literal price / capability among current models above a capability floor (≥45) to avoid a $0.002 utility model winning on a tiny denominator. A cheap low-capability model can be Pareto-efficient without being a good executor — both statements can be true.

    3. The yellow line — the strict frontier

    A configuration X dominates Y iff X is both cheaper and ≥ as capable with one coordinate strictly better. The frontier is the undominated set — 14 points in this snapshot after the GLM-5.2 correction (previously 14, now composition changed). In ordinal order from cheapest:

    The correction that moved GLM-5.2 max into position 7 (previously priced at $0.37, 1.4/4.4) is the single largest price move in this refresh: with the documented Kilo drop to $0.07 input / $0.22 output per million, its task price falls from $0.37 to $0.0147, making it the cheapest A-tier frontier point and the literal best $/capability among executor-eligible models (≥47). Muse Spark 1.2, which previously held that rank, shifts to #2 while remaining the left-most S-tier frontier anchor. The yellow polyline is drawn in that sorted X order; its monotonicity is guaranteed by construction, not by smoothing.

    4. Reading provider lineages — why lines matter

    Each hue is a provider (Anthropic, OpenAI, Z.ai, Xiaomi, Kimi, IBM, plus open-weights). Within a provider, a polyline connects the same family across efforts (e.g., Opus 5 low→med→high→xhigh→max, Sol non-reasoning→low→med→high→xhigh→max, GLM-4.7 non-reasoning→reasoning→5.2 max, Muse 1.1→1.2). Multiple hues for one provider mean distinct lineages (Z.ai has GLM-4.5 vs GLM-5.2 vs GLM-4.7 Flash; Xiaomi has MiMo-V2.5 vs V2.5-Pro; OpenAI has GPT-5.4/5.5/5.6 families). If a plausible free variant exists, the lineage helps you avoid paying for a dominated effort inside its own family: Opus 5 max is dominated by Opus 5 xhigh (both 63 AA, xhigh $1.80 vs max $2.34), and Sol non-reasoning is dominated by Sol low — neither should be a default route unless a niche benchmark justifies it.

    All labels are shown for points with capability ≥47 (A and above) in the default “Focus: ≥ Muse 1.2” view. That threshold is chosen to keep the frontier and its immediate contenders legible while hiding the dense D-tier utility cloud that otherwise overwhelms the canvas. Switch to “Show all” or “Frontier only” in the dropdown to audit the full extent or isolate the yellow line.

    5. Executor rank vs frontier — and the Muse 1.2 case

    Executor rank answers lowest dollars per capability point among current, priced, ≥45: GLM-5.2 max (3485 cap/$) → Muse Spark 1.2 xhigh Contributor (2689) → Luna high (2350) → DeepSeek V4 Flash max (1733) → Grok 4.3 high (497). Without the ≥45 floor, GLM-4.7 Flash non-reasoning wins at 4019 cap/$ — cheaper per point but at 15.5 capability it cannot serve an executor role. The floor is policy, defined in project-config.json, and is shown in both tables so the denominator effect is auditable.

    Muse Spark 1.2 is deliberately priced at its Contributor/data-sharing SKU ($0.10 / $0.002 / $0.20 → $0.021 task) as the primary coordinate. The Standard/no-sharing SKU ($1.25 / $0.15 / $4.25 → $0.40 task) is retained as secondary evidence in the CSV and hover metadata. That choice preserves the workload while repricing the token schedule — it is why Muse sits off-left as the cheapest frontier point above GLM-5.2, not because its token burn differs.

    6. External cross-checks — not votes

    Three separate planes are rendered below the main graph precisely so they are not mistaken for additional votes on the same metric: AA Intelligence Index vs direct task cost; Kilo terminal/coding completion vs cost/attempt; Vals Index vs cost/test. Matching frontier curvature across planes raises confidence; divergence exposes harness specialization (a model that wins on terminal coding may not win on breadth intelligence). Each links to its live explorer.

    8. How to use this page without fooling yourself

    Start with the frontier graph. Use the Focus: ≥ Muse 1.2 toggle to keep the A-tier and above legible — that is the region where an extra dollar actually buys capability you can feel in a real task. Hover any dot for calibrated capability, task price, and provenance; click to pin the full source list, models.dev specs, and context window. The legend toggles provider hues, and the Provider lines checkbox traces each family. If you are choosing between two nearby dots on the same lineage (e.g., Kimi K3 high vs max, or Sol xhigh vs max), the line tells you whether the price step is paying for capability or just verbosity. A steep vertical segment with little horizontal movement is pure capability; a shallow horizontal segment is price without capability — skip it.

    Next, read the Pareto table that sits immediately below the graph, before any executor ranking. If a model you like is not on that table, ask why: it is dominated, meaning something else is both cheaper and at least as capable. The “dominated by” column in the near-frontier table names that something else, with capability gap and price premium, so you can decide whether the dominated model offers a non-price advantage (latency, context length, open weights) that justifies the premium. If it does not, do not use it.

    Then — and only then — look at executor rank. The executor table is a single scalar sort with an explicit floor. Change the floor mentally: if you raise it to S-tier (≥56) you get a pure frontier bake-off; if you lower it to B-tier (≥40) you invite MiMo-V2.5 and Luna medium into the shortlist. Both views are shown (frontier-eligible top-5 vs global no-floor top-10) so the denominator policy cannot hide. The same logic applies per-effort inside a family: the Luna table shows high ($0.000425) beating xhigh and max on $/capability, even though max wins on raw capability. Choose the knee, not the max, unless the extra 2 points are worth 67% more cost.

    9. Data quality and what remains uncertain

    27 source_ids feed this build, but not all evidence is equal. The calibration report (embedded in calibrated_model_observations.csv as anchor_count and rmse) makes that visible: a mapping fitted on 3 anchors with RMSE 0.18 is less trustworthy than one on 12 anchors with RMSE 0.04. The most anchored groups are legacy-AA overlaps (dozens of shared models); the thinnest are single-vendor scorecards (Qwen 3.8 Max, DeepSeek V4 Flash model card) with 4–7 anchors each, fitted in log-cost space to reduce outlier leverage. Those thin groups carry lower source_weight_overrides (0.35–0.45) versus Vals Terminal-Bench at 1.0, so a noisy benchmark cannot drag the aggregate.

    Task price remains the largest uncertainty for low-volume models. Direct measured task cost exists for frontier families and for the new Kilo/Vals indices, but many catalog entries rely on the standardized token-price proxy. That proxy is not a bill; it is a reproducible estimate mapped to AA task dollars through overlapping models. Its weight is 0.35 versus 0.65 for the AA token-count proxy, and both are dominated by direct task-cost evidence where present. When you see a model with 1–2 carets and a single cost source, treat its X as a calibrated estimate and check the hover’s cost_sources list — if it says only standard-task-price-proxy-v7, assume ±30% price uncertainty is honest. GLM-5.2’s move to $0.0147 is a price-schedule shift, not a new measurement; the next direct Kilo task-cost ingestion for GLM-5.2 will tighten that X further.

    Finally, remember what the frontier is not: it is not a recommendation, not a benchmark leaderboard, and not stable across tasks that change the cost mix. A coding agent that burns 40k output tokens per task will shift the frontier toward input-cheap models; a chat workload with 2k output will favor output-cheap ones. The effort multipliers are intentionally exposed in project-config.json so you can re-tune the task profile and re-run calibrate.py for your workload instead of arguing about a single universal frontier. That is why the graph is biggest: you need to see where your workload pushes the yellow line.
